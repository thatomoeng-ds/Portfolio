Car Allowance Dashboard

A browser based financial engine that reimplements a multitab Excel employee vehicle scheme. No macros, no server, just a single HTML file

Internal Automation Project

The Car Allowance Dashboard recreates a heavyweight, formula locked Excel workbook, a company car / employee vehicle finance scheme spread across 8+ linked worksheets as a single, self contained HTML application that runs entirely in the browser. Instead of asking finance analysts to open, unprotect, and manually rekey figures into a fragile "New Scheme" tab for every model, the dashboard reads the raw source workbooks directly, faithfully reimplements every formula in JavaScript, and renders a live, auditable breakdown with the row by row logic annotated against the exact Excel cell references it replaces (C15, C24, C39, C93, C112 and more).

The Problem

The "New Scheme" tab of the source workbook is the single source of truth for whether offering a particular vehicle on the employee scheme is financially viable but it's a hand built Excel model full of hard coded VLOOKUPs into seven other tabs, a specific column layout that silently breaks if a sheet is reordered, and it only ever shows one model at a time. Getting a portfolio-wide view meant either manually pasting dozens of models through the same protected tab, or trusting a stale, months old summary. There was no fast way to answer: "which models are costing us money on this scheme right now, and by how much?"

My Approach & Thought Process

  • Treated the Excel tab as a specification, not a black box. Rather than trying to read live formulas out of the workbook, I opened the "New Scheme" tab cell by cell and rederived every row's logic cost of the vehicle (C15–C28), loan value to the employee (C34–C50), monthly cost (C56–C58), group profit/loss (C77–C95), and company profit/loss (C101–C114) then reproduced each one as a plain JavaScript expression, keeping the original cell reference as a code comment so the two can always be checked against each other line by line.
  • Read source values by position, not by trusting labels. Several sheets repeat header text (e.g. more than one "Description" column) so name matching alone is unreliable. I mirrored the workbook's own approach: a cell(sheetKey, tais, colLetter) helper reads a value by its exact Excel column letter (converted to a zero based index), exactly as the original VLOOKUPs do e.g. duty is December!AU + December!AV, dealer billing retail is Dealer Billing!I.
  • Built a fuzzy header token matcher for the identity/label fields. Fields that are just for display (description, brand, segment, e-series) don't need to be pixel perfect, so those are resolved by tokenising column headers (upper casing, splitting on non alphanumerics) and matching against a target word list this way the dashboard tolerates minor header renames across monthly file refreshes without needing a code change.
  • Modelled two parallel financial "spines" from one set of inputs. The workbook distinguishes a Profitability View (includes service costs and refurbishment, excludes the motorplan balance) from a Tax View (includes the motorplan balance, excludes service/refurbishment). I built both as separate result objects (pv and tv) computed from the same underlying vehicle figures, so neither view can silently drift out of sync with the other.
  • Made the viability verdict explicit and auditable. Every model gets a plain English status, "Structure is economically viable" vs. "Structure results in economic loss" derived directly from the sign of the computed profit figures (company benefit > 0 and group profit ≥ 0 = VIABLE), shown as colour coded badges instead of forcing the reader to interpret raw numbers.
  • Designed three ways to get data in, for three real workflows. Drag and drop for a one off check, a live folder watch (File System Access API, polling every 10 seconds) for an analyst who keeps the shared drive open, and a published JSON snapshot polled every 60 seconds for anyone who just wants to view the current numbers without touching any files at all.
  • Built a volume weighted Executive Summary on top of the same engine. Rather than reviewing models one at a time, the "Executive Summary" tab recomputes every car in the loaded file(s), joins in planning volumes, and rolls the whole scheme up into a viable/not viable portfolio ladder, surfacing the highest volume non viable models first, since those are the biggest euro exposure to fix.

Key Features

  • Client-side parsing of .xlsb / .xlsx / .xlsm source workbooks, no upload, no backend, data never leaves the browser
  • Faithful line by line reimplementation of a 100+ row Excel financial model, each figure traceable back to its original cell reference
  • Fixed column (VLOOKUP equivalent) reads for every financial figure, plus a fuzzy token matcher for display only identity fields
  • Two parallel calculated views (Profitability & Tax) sharing one set of source inputs
  • Editable overall assumptions (loan term, interest rate, commission, VAT, insurance) with instant recalculation across every loaded model
  • Executive Summary tab: volume weighted viable/not viable roll up with the biggest non viable exposures called out automatically
  • Three independent data loading paths (manual upload, live folder watch, published JSON feed) plus one click CSV export

Impact

  • Turned a single model, protected Excel tab into an instant, portfolio wide viability check across every model in the scheme
  • Removed the need to manually rekey figures through the workbook for each model, the dashboard reads all 8+ source sheets directly
  • Surfaces the highest volume loss making models automatically, instead of relying on ad hoc manual review
  • Zero deployment footprint, a single HTML file that runs offline in any modern browser, with no license, install, or server cost
  • Every computed figure is traceable back to its exact Excel cell reference, keeping the model auditable against the original workbook
