Hackaprompt Cost of Retail Dashboard

Self-contained interactive HTML dashboard for retail cost & volume reporting

Hackaprompt Use Case

The Cost of Retail (CoR) Dashboard is an end-to-end data engineering and analytics project I built during a Hackaprompt use-case challenge: a Python ETL pipeline that ingests multiple heterogeneous Excel data sources, resolves business logic that would normally live inside a BI tool, and compiles everything into a single, self-contained, interactive HTML analytics application. No server, no database, no BI license, and no live connection required to view it.

The Problem

The business needed a recurring view of retail volumes and cost-of-retail performance across product categories, individual models, and sale types (new vs. used), but the numbers that make that view meaningful live scattered across a dozen different files: a main transactions export, a separate parameters workbook with seven distinct target tables, six monthly margin workbooks, and an external planning file for category level targets. Reconciling all of this by hand every reporting cycle was slow, error prone, and impossible to share with anyone who didn't have a BI license or direct access to the raw files.

My Approach & Thought Process

  • Reverse-engineered the data model before writing a single chart. I audited every source workbook column by column and documented exactly which fields mattered period, transaction type, sale type, model code, category, net retail, and cost mapping each one to a named constant so the extraction logic stayed transparent and safe to rerun every month.
  • Consolidated seven separate target tables into one coherent join. Margin, support, rate, and net-retail targets each lived in their own block of a parameters sheet, keyed by model code and month. I wrote a dedicated extractor for each block and joined them all back to the transaction level records by model code, the kind of multi source entity resolution that turns disconnected spreadsheets into a single trustworthy dataset.
  • Made a deliberate architecture trade-off: compute targets client side, not at build time. Because targets vary by month, baking a single "actual vs. target" number into the build would have meant re-running the whole pipeline every time someone changed the month filter. Instead, I embedded the full month by model target lookup tables as JSON and resolved them in JavaScript at render time, keeping the dashboard instantly interactive without sacrificing accuracy.
  • Designed for a "single file, zero dependency" output. All filtering and interactivity runs client side in the browser, with every data table embedded as JSON directly inside the HTML. The finished dashboard opens in any browser with no installation, no login, and no network dependency which is ideal for sharing with stakeholders who don't have BI tool access.
  • Built KPI cards that tell the story at a glance: retail sales volume, contribution margin, new item margin, and used item margin, each with a target vs actual sub-label so a viewer immediately sees whether performance is on track without digging into charts.
  • Layered in visual analytics with Chart.js: a cost percentage gauge benchmarked against the quarterly target, a stacked bar chart breaking down volume/cost by category and month, and a model level chart for granular drill down, all re-rendered client side whenever a filter changes, with an additional ranking view surfacing the best and worst performing models by margin-per-unit each month.
  • Solved a real image-quality problem with automated computer vision style cleanup. Reference product images arrived with inconsistent banners and backgrounds. I wrote a Pillow based pipeline that samples pixel regions to detect and crop banner strips, builds an edge background mask to distinguish subject from background, and caches a cleaned version of every image, so the dashboard always displays a consistent, professional visual regardless of source photo quality.
  • Treated it like a production release, not a one off script. The generator writes a single reproducible HTML output every time it runs, so refreshing the dashboard against a new month's data is a one command rebuild. I tracked the build script's evolution with Git version control, committing incrementally as each extractor and chart was added, turning what used to be a manual, multi-workbook exercise into a repeatable, auditable process with the raw data always traceable back to source.

Key Features

  • Fully client-side filtering by category, model, sale type, and month, no page reloads or server round trips.
  • Live KPI cards for volume, contribution margin, new margin, and used margin, each compared against a dynamically resolved target.
  • A cost % gauge chart benchmarked against quarterly and category specific targets pulled from a separate planning file.
  • Stacked category breakdown chart with per month detail across the full reporting period.
  • Model level drill down chart plus a best/worst margin per unit ranking for the current month.
  • A second exec summary tab with headline total / new / used volume and cost% KPIs.
  • Automated reference image cleanup pipeline (banner cropping + background masking) using Pillow.
  • Single self contained HTML output which is shareable via email or a shared drive, opens in any browser.

Impact

  • Reduced monthly reporting preparation from an estimated ~4 hours to ~15 minutes per cycle, a single command replaces manual cross referencing.
  • Automated consolidation across 20+ Excel worksheets and 10+ source files, spanning 4 different file formats (.xlsx, .xlsm, .xlsb).
  • Eliminated an estimated 90% of manual data preparation effort previously spent reconciling seven separate target tables and six monthly margin workbooks by hand.
  • Removed the dependency on BI licensing for distribution entirely, any stakeholder can open the finished dashboard in a browser with zero setup.
  • Made the reporting process reproducible and auditable, with every figure traceable back to its original source file.
